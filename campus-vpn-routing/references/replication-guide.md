# 开启 VPN 后浙大网站打不开：ZJU 专用复刻教程

本 skill 仅针对 `zju.edu.cn` 和全部子域名。这次最终解决的是整个浙大域名，而不是几个固定页面。可复刻的方法是：对照实际出口、用域名后缀统一分流、验证最终生效的配置、在必要时恢复旧 IP 连接中的主机名。下面的具体结果来自 2026-09-26 的本机排查；当时可用的代理不代表其他网络环境访问浙大也应使用代理。

## 1. 这次看到了什么

| 检查 | 结果 | 可得出的结论 |
| --- | --- | --- |
| 首条规则为 `DOMAIN-SUFFIX,zju.edu.cn,DIRECT` | 规则已保存、模式为 rule、TUN 开启 | 不是简单的“忘记保存” |
| 研究生院和 WebVPN 在当前连接上测试 | TLS 关闭或超时 | 还不能只凭错误定位 DNS、学校封禁或 VPN |
| 临时关闭 TUN，确认接口为 Wi-Fi `en0`，按真实地址复测 | 两个站点连接超时，随后恢复 TUN | 当时的真实直连路径不可用；不是只靠绕过 TUN 就能恢复 |
| 用现有代理测试，并随后实际访问原 URL | 代理路径可用 | 可以用经过验证的代理作为域名出口 |
| 只给研究生院和 WebVPN 加例外后，DSKE 仍报错 | 原有浙大全域名直连规则还在 | 逐站点修补没有满足 `*.zju.edu.cn` 的原始范围 |
| `dig` 返回新的虚拟地址，但系统连接仍用 WebVPN 的真实地址 | 域名规则可能无法命中这条无域名连接 | 需处理缓存/域名识别，不应长期硬编码每个网站 IP |
| 全局后缀规则加域名嗅探后 | DSKE、研究生院和主站返回 200；WebVPN 登录重定向为 302；指定 WebVPN 真实 IP 的测试也返回 302 | 支持全域名策略和旧 IP 兼容机制在这次案例中生效 |

DSKE 最后在 Edge 中显示了完整 Teams 页面与图片。这里没有证明学校限制了某个来源 IP，也没有证明所有失败都由 DNS 引起。另一个订阅的代理组映射已检查，但没有实际切换后验证其网络连通性。

## 2. 修改前先保留可回退的配置

在 Clash Verge Rev 的“订阅”页面查看当前订阅，记录代理模式、TUN/系统代理开关、当前代理组。复制全局扩展脚本、全局覆写、当前订阅的规则扩展与订阅脚本到本地备份，不导出或分享订阅 token、节点密码或 Cookie。若已有自定义 `main`，把新逻辑合并到原函数，不能整段覆盖原有脚本。

这次全局脚本和两个订阅的脚本原先都只是 `return config`，因此可以加入新逻辑。清理的单域名、直连与固定 IP 规则也是本次排障创建的，未清空用户原有的其他规则。

## 3. 先决定用直连还是代理

在终端使用同一个公开页面做测试。以下命令不提交账号或登录表单，输出状态码即可：

```sh
curl -sS -L -o /dev/null -w 'HTTP %{http_code}\n' \
  --connect-timeout 8 --max-time 20 'https://dske.zju.edu.cn/teams/'

curl -sS -L -o /dev/null -w 'HTTP %{http_code}\n' \
  --proxy http://127.0.0.1:7897 \
  --connect-timeout 8 --max-time 20 'https://dske.zju.edu.cn/teams/'
```

`7897` 是本机当时的混合代理端口，复刻时从设置读取实际端口。第一条是“当前网络路径”，在 TUN 开启时不能称为真实直连；`--noproxy '*'` 也不能绕过 TUN。

若需要隔离 TUN 影响，保存当前状态，短暂关闭 TUN，确认实际路由，再复测并立即恢复。macOS 可用下面的只读查询确认接口：

```sh
route -n get <刚查询到的服务器真实IPv4>
```

不要硬编码本例的服务器 IP 到其他校园站点。如果终端缺少网络权限，工具应按环境申请权限，而不是把沙箱中的 DNS 错误当成网站故障。对外发送的测试仅应包含任务所需公开 URL；不要拿已登录的敏感页面作测试样本。

直连成功就使用 `DIRECT`。直连失败、代理成功才使用相应代理组。若两条路都不通，继续定位服务器、校园内网、学校身份认证或当前网络问题；需要学校官方 VPN 的服务不能用商业代理替代。

## 4. 用整个域名作为规则

这次选择了代理组 `节点选择`，核心规则为：

```yaml
rules:
  - DOMAIN-SUFFIX,zju.edu.cn,节点选择
  # 原有规则继续保留在后面
```

这个后缀规则涵盖主域名、`dske.zju.edu.cn`、`yjsy.zju.edu.cn` 和更深的子域名。写入内容不需要 `*.`；`DOMAIN` 只匹配单个完整域名。[mihomo 路由规则文档](https://wiki.metacubex.one/config/rules/)说明了匹配类型及从上到下的优先顺序。

在当前 Clash Verge Rev 中，新版扩展机制的前置规则编辑器与全局脚本是不同入口，旧教程中的全局 Merge `prepend-rules` 不能直接照搬。覆写 `rules` 数组还可能丢失其他规则。需要跨订阅复用时，通过脚本前插新规则并保留原数组，参见[扩展配置与执行顺序](https://www.clashverge.dev/guide/extend.html)。

## 5. 在客户端中应用全局脚本

1. 打开“订阅”，在“全局扩展脚本 / Script”卡片上右键，选择“编辑文件”。这是全局扩展入口，不是切换网络代理模式到“全局”。
2. 阅读并复制现有脚本作为备份，然后打开随 skill 附带的 [脚本模板](../assets/global-domain-routing.js)。已有脚本时合并 `main` 的逻辑；空白模板时可以使用完整脚本。
3. 模板中的域名固定为 `zju.edu.cn`。调整 `proxy` 或 `direct`、订阅名称到实际代理组的映射。模板中的 `魔戒.net → 节点选择`、`uuone → uuone` 是这次检查过的组名；其他订阅必须自行确认并添加映射。
4. 如对照结果涉及旧 IP 丢失域名，保留 `RECOVER_HOSTNAME_FROM_CACHED_IP = true`；没有这个证据时设为 `false`。保存前检查已有嗅探配置，避免破坏别的应用依赖的跳过设置。
5. 保存，查看是否有脚本或内核错误。若规则没有刷新，使用“重新激活订阅”，不必重新下载整个订阅。
6. 检查订阅自己的规则编辑器、覆写配置和脚本，移除本次建立的冲突规则，例如更优先的 `DOMAIN-SUFFIX,zju.edu.cn,DIRECT`。保留其他已有规则。

模板会在代理组未配置或不存在时明确报错，避免把未知订阅的第一个策略组误当成可用代理。这比本次现场脚本的自动取首个组更适合长期复用。

全局扩展之后还有订阅扩展，最终结果必须以“查看运行时订阅”和连接记录为准。脚本的合并方式参见[Clash Verge 全局脚本文档](https://www.clashverge.dev/guide/script.html)。

## 6. 为什么还需要识别缓存的真实 IP

TUN 的 fake-IP 将域名映射到虚拟地址。`dig`、系统 DNS、浏览器缓存可以暂时给出不同结果；访问者也可能使用安全 DNS。浏览器若连接旧的真实 IP，内核不一定知道它属于哪个域名，后缀规则就可能失去匹配依据。

在这次排查中，清除系统缓存没有立即恢复 WebVPN。最后启用 HTTP、TLS、QUIC 的主机名识别，并使用 `parse-pure-ip: true`，使一部分原本只带 IP 的连接能重新获得域名。通过 `curl --resolve` 指定已知真实 IP 的测试成功，支持这个机制在本例中有效。[mihomo 域名嗅探文档](https://wiki.metacubex.one/config/sniff/)定义了这些字段。

```yaml
sniffer:
  enable: true
  parse-pure-ip: true
  override-destination: false
  sniff:
    HTTP:
      ports: [80, 8080]
    TLS:
      ports: [443, 8443]
    QUIC:
      ports: [443, 8443]
  force-domain:
    - '+.zju.edu.cn'
```

这里的 `force-domain` 强制识别浙大域名，但 `parse-pure-ip` 对其他未获得域名的流量也生效，不能说整个嗅探功能只影响浙大。它依赖连接中可识别的主机名，不是 TLS 解密，也无法保证处理所有 IP 连接或隐藏服务器名的情况。应以必要性和验证结果决定是否开启。

## 7. 怎样证明“已经修好”

在运行时配置中确认后缀规则位于靠前位置，出口正确，之前的冲突规则没有再次排在它之前。连接页面按校园域名筛选，确认链路是选定代理组或 `DIRECT`，而不只是查看编辑文件。

测试原始报错页面，再抽查不同业务的子域名和主站。这次样本为 DSKE、研究生院、WebVPN 与浙大主页；样本是验收点，配置中不需要列出全部网站。对 WebVPN，根地址返回 302 到 `/login` 是预期行为，随后还需看到登录页；不必代替用户登录。

最后刷新浏览器中的原标签页，查看正文、关键图片和必要接口是否加载。`200` 可能只是空壳页面或错误页，保存成功和节点延迟正常也不能代替浏览器验证。如果用户要求所有订阅，检查每个订阅的映射；真正切换后的连通性若没有测试，报告中要明确区分。

## 8. 回退和复用

回退时恢复之前备份的全局脚本、任务修改的订阅规则和嗅探配置，重新激活订阅，核对 VPN 开关和模式。不要通过“重置全部配置”回退局部改动。

复刻到另一台设备或另一条网络时，保持域名范围为 `zju.edu.cn`，重新确认代理组映射和直连/代理对照，不能沿用本例 IP、端口、服务 socket 或控制密钥。核心经验是维护一个完整浙大域名策略，并验证最终生效链路；网络环境改变后，出口选择也可能需要重新评估。本 skill 不提供迁移其他学校域名的工作流。

安装此 skill 后可使用：`请用 $campus-vpn-routing 排查开启 VPN 后浙大网站无法访问的问题，覆盖 *.zju.edu.cn，完成浏览器验证。`
